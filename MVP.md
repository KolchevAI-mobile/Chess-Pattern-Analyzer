# MVP v0.1 — «Диагноз за 5 минут»

## Одна фраза

Приложение, которое за один сеанс говорит шахматисту 800–1400: **«твоя главная повторяющаяся
ошибка — X, вот три партии, где она стоила тебе результата»** — и делает первый шаг к её исправлению.

## Какую гипотезу проверяем

Ценность продукта — не в анализе одной партии (это уже умеют Chess.com и Lichess), а в **связи
ошибок между партиями**. MVP проверяет ровно это: готов ли пользователь платить вниманием
за «сквозной диагноз», а не за ещё одну стрелку «зевок».

Отсюда границы: минимум механик вокруг, максимум качества диагноза.

## Решения по M1 (согласованы 2026-11-12)

| Вопрос | Решение |
|---|---|
| Авторизация | Только ник + публичные партии Lichess. OAuth — веха M2 |
| Режимы | rapid обязателен, blitz опционален, bullet исключён (нет осмысленных часов) |
| Объём | 20 партий на MVP. 50 партий и очередь — M2 |
| Тренировка | В M1 не входит: только импорт, разбор и диагноз. Задачи — M2/M3 |
| Глубина анализа | Жёсткий потолок depth = 10 (в ML это `MAX_DEPTH`), поднимается позже |
| Таймаут клиента | HTTP-запрос Android — 120 с: бэк на слабом CPU может думать минутами |

## Пользовательский сценарий (5 минут)

1. Установил приложение → ввёл ник Lichess (публичные партии, без пароля).
2. Выбрал «последние 20 партий, rapid» → «Анализировать».
3. Видит прогресс: 30–90 секунд локально и до 5 минут на слабом сервере (клиент ждёт до 120 с).
4. Экран **«Диагноз»**:
   - главный паттерн + одним предложением, что он значит;
   - `confidence` человеческим языком: «уверенно» / «данных пока мало»;
   - 2–3 доказательства: партия, ход, оценка до/после;
   - вторичные паттерны списком;
   - разбивка ошибок по фазам.
5. Тап по доказательству → партия с подсвеченными ошибками (ход, cp-loss, остаток времени).
6. Блок «Что делать» — 3 конкретные рекомендации текстом. Интерактивные задачи — уже M3,
   в MVP честно написано, что тренировки появятся дальше.

## Границы MVP

| Входит | Не входит (сознательно) |
|---|---|
| Импорт партий Lichess по нику (public API; rapid и blitz) | Chess.com — авторизация и импорт (M6); приватные партии; bullet |
| Stockfish depth ≤ 10 (жёсткий потолок), кэш разбора | Maia, «человеческие» оценки |
| 4 детектора паттернов + «надлом» как сырая метрика | Обученные ML-модели, формальное определение надлома |
| PostgreSQL, миграции, хранение партий и разборов | Очередь и пул воркеров (M2) |
| 3 экрана Android: ввод ника, список партий, диагноз | Тренировки, задачи, SRS (M3) |
| Анонимный профиль (device token + ник) | Пароли, соцвход, мультиустройство |
| Docker Compose для локального запуска | Прод-инфраструктура, CI/CD, мониторинг (M1.5) |

## Технические решения и почему именно так

| Решение | Альтернатива | Почему |
|---|---|---|
| Анализ синхронный, ≤ 20 партий на запрос | Очередь сразу | 20 партий × depth 10 ≈ 30–90 с на нормальной машине; очередь добавляет инфраструктуру, не проверяя гипотезу |
| depth жёстко ограничен 10 | depth 12–16 «для качества» | На бесплатных 1–2 vCPU (Render/Railway) разбор 20 партий при depth 12+ — это 3–5 минут; 10 — компромисс |
| Таймаут HTTP-клиента Android — 120 с | Дефолтные 30 с | Лучше показать прогресс и дождаться, чем упасть с таймаутом на медленном бэке |
| `payload` храним целиком, но списки отдают сводку | Отдавать payload в списках | 20 партий с историей ходов — это мегабайты; Android получит фриз, а трафик — счёт |
| PostgreSQL с первого дня | SQLite | Общая БД для Kotlin и Python — как в паспорте; миграции и JSONB нужны обоим |
| Lichess public API без OAuth (M1) | OAuth-вход | Публичных партий достаточно для первого диагноза; OAuth — M2, когда понадобятся приватные
| Анонимный device token (JWT без пароля) | Полноценные аккаунты | Убирает экран регистрации; JWT остаётся, чтобы формат не менялся задним числом |
| Кэш по SHA-256 PGN | Без кэша | Повторный импорт и повторный анализ не должны жечь CPU |
| Один ML-процесс, движок под блокировкой | Пул воркеров | На MVP хватает; узкое место осознанно переносится в M2 |
| «Надлом» показываем как сырую метрику | Показывать как диагноз | Формального определения нет — нельзя выдавать гипотезу за вывод (см. Passport.md) |

## Модель данных (M1)

```
users(id, device_token_hash, lichess_nick, created_at)
games(id, user_id, source, external_id, pgn, sha256, white, black, result,
      time_control, played_at)
analyses(id, game_id, engine, engine_depth, analysis_version, accuracy,
         avg_cp_loss, payload jsonb, created_at,
         UNIQUE (game_id, analysis_version))
pattern_hits(id, user_id, code, title, severity, confidence, summary,
             evidence jsonb, computed_at)
jobs(id, type, status, progress, error, created_at, started_at, finished_at)
```

`payload` — тот же ответ ML (`games[]`), чтобы клиент не ходил в два места.
`analysis_version` + `engine` позволяют пересчитать разбор, когда меняется методика.

**Про размер `payload`.** Один разбор 20 партий — это мегабайты JSON: ходы, оценки, доказательства.
Поэтому правило: `payload` хранится целиком (jsonb переживёт), но **списки его не отдают**.
`GET /api/v1/games` возвращает сводку (точность, зевки, ошибки, дата), а ошибки конкретной партии
приходят постранично из `GET /api/v1/games/{id}`. Иначе Android будет парсить мегабайты на список.

## API-контракты

### Backend

```http
POST /api/v1/import
{ "platform": "lichess", "username": "nick", "limit": 20, "perf_type": "rapid" }
→ 200 { "player": "nick", "games_imported": 20, "games_analysed": 20,
        "duration_ms": 74000, "patterns_found": 2 }

GET /api/v1/games?limit=20
→ [{ "id": "...", "white": "...", "black": "...", "result": "1-0",
     "accuracy": 81.0, "blunders": 2, "mistakes": 6, "played_at": "..." }]

GET /api/v1/games/{id}?errors_offset=0&size=20
→ { "id": "...", "white": "...", "black": "...", "result": "1-0",
    "accuracy": 81.0, "breaking_point": {...},
    "errors": [{ "ply": 30, "san": "Nxd7", "cp_loss": 1000, "phase": "middlegame" }],
    "errors_total": 8 }

GET /api/v1/insights
→ { "player": "nick", "games_analysed": 20, "generated_at": "...",
    "patterns": [{ "code": "phase_gap", "title": "Слабое место: миттельшпиль",
                   "severity": 0.9, "confidence": 0.7,
                   "summary": "...", "evidence": [{ "game_id": "...", "ply": 30, "san": "Nxd7" }] }],
    "breaking_point": { "games_with_breaking_point": 7, "median_ply": 48, "dominant_phase": "middlegame" } }
```

На M1 импорт синхронный (`200`): очередь и `202 + job_id` появятся в M2 вместе с `/api/v1/jobs`.

### Lichess API: два обязательных параметра

```
GET https://lichess.org/api/games/user/{nick}?max=20&perfType=rapid&clocks=true
Accept: application/x-chess-pgn
```

- `perfType` (не `time_control`) — `rapid` или `blitz`; bullet не запрашиваем.
- `clocks=true` — **без него Lichess не отдаст `%clk`**, а значит не сработает детектор
  `time_trouble`. Это не опция «на потом», а условие работы одного из четырёх паттернов.

### ML (уже реализовано)

```http
POST /api/v1/analyze   { "pgn": "...", "player": "nick", "depth": 10, "max_games": 20 }
→ { "meta": {...}, "games": [...], "patterns": [...], "breaking_point": {...} }
```

Внутренний вызов backend → ML стоит делать пакетно (`POST /api/v1/analyze/batch`), чтобы
импорт 20 партий был одним HTTP-вызовом, а не двадцатью.

## Как выбирается «главный» паттерн

1. Считаются все детекторы; каждый отдаёт `severity` (0..1) и `confidence` (0..1).
2. Сортировка по `severity × confidence`.
3. Первый — диагноз; 2–3 следующих — список «ещё замечено».
4. Если `confidence < 0.3` — вместо уверенного тона показываем «данных пока мало,
   сыграйте ещё 5 партий»: ложный диагноз хуже отсутствия диагноза.

Тексты пишем от второго лица и без движковых терминов:

- `conversion_collapse` → «Ты теряешь перевес: 4 из 7 партий с оценкой +2 и больше не выиграны».
- `time_trouble` → «В цейтноте ты ошибаешься в 2.3 раза дороже, чем при нормальном времени».
- `opening_leak` → «Дебют стабильно стоит тебе ~0.6 пешки ещё до миттельшпиля».
- `phase_gap` → «Основные потери — в миттельшпиле; дебют и эндшпиль заметно чище».

## Критерии приёмки

| # | Критерий |
|---|---|
| AC1 | `docker compose up` поднимает Postgres, backend и ML; `/health` всех трёх — 200 |
| AC2 | Импорт и разбор 20 партий при depth 10: на локальной машине ≤ 90 с, на 1–2 vCPU (free tier) ≤ 5 мин; клиент ждёт до 120 с и показывает прогресс |
| AC3 | Экран «Диагноз» показывает топ-паттерн с ≥ 2 доказательствами (партия + ход + оценка) |
| AC4 | Повторный импорт тех же партий не запускает анализ заново (кэш по SHA-256) |
| AC5 | Пустой/несуществующий ник, лимит Lichess, недоступный движок — понятные сообщения, не 500 |
| AC6 | Партия открывается из доказательства с подсветкой ошибочных ходов |
| AC7 | `pytest` и `gradlew test` зелёные; сборка APK проходит в CI |
| AC8 | Удаление профиля удаляет партии и разборы (приватность) |

## Демо-сценарий (для показа инвесторам/друзьям)

1. Открыть приложение, ввести боевой ник (20+ партий rapid).
2. Показать прогресс и появившийся диагноз.
3. Открыть доказательство → показать конкретный ход, где ушёл перевес.
4. Сравнить с тем, что говорит Chess.com по той же партии (там будет «зевок», без связи с другими).

## Порядок работ (без сроков)

Даты не планируем: важен порядок и то, что каждый шаг проверяем до перехода к следующему.

1. **Стенд и данные.** `docker-compose` с Postgres, миграции Flyway, сущности `games`/`analyses`.
2. **Импорт.** Клиент Lichess (`perfType`, `clocks=true`), `POST /api/v1/import`, идемпотентность по `(source, external_id)`.
3. **Разбор.** Backend → ML одним batch-вызовом, `analyses` с `analysis_version`, кэш по SHA-256, depth ≤ 10.
4. **Витрина.** `GET /api/v1/games` (сводка), `GET /api/v1/games/{id}` (ошибки постранично), `GET /api/v1/insights`.
5. **Клиент.** Сеть и DI, таймаут 120 с, экран ника → список партий → «Диагноз» → переход к ошибке.
6. **Полировка.** Ошибки внешнего мира, прогресс, CI.
7. **Приёмка.** Пройти AC1–AC8 на живом аккаунте и записать результат.

Шаг не закрыт — следующий не начинаем: иначе легко получить три недоделанные части вместо одной рабочей.

## Метрики успеха MVP

- ≥ 60 % тестовых пользователей получают ≥ 1 паттерн с `confidence ≥ 0.4`.
- Время «установка → диагноз» ≤ 5 минут.
- ≥ 40 % пользователей открывают хотя бы одно доказательство (значит, диагноз задел).
- Экспертная оценка 30 отчётов: ≥ 60 % паттернов признаны осмысленными.

## Риски MVP и ответ

| Риск | Ответ |
|---|---|
| На 20 партиях паттерны шумят | `confidence` + минимумы выборки в детекторах; честный текст вместо ложной уверенности |
| Stockfish не успевает | depth 10, кэш, ограничение 20 партий; очередь — M2 |
| Lichess API rate limit | ≤ 1 запрос/с, backoff, импорт порциями по 20 |
| Пользователь ждёт и уходит | прогресс с процентами, «можно свернуть» |
| Диагноз не совпадает с ожиданиями пользователя | показывать доказательства, а не оценки; собирать фидбек «согласен/нет» на карточке |

## Принятые решения и открытые вопросы

Решено 2026-11-12: ник без OAuth (OAuth — M2); rapid обязателен, blitz опционален, bullet исключён;
20 партий на MVP; тренировка — M2/M3; depth ≤ 10; таймаут клиента 120 с.

Осталось открытым:

1. **Нужен ли веб-кабинет?** Для отладки хватает Swagger ML и JSON; кабинет — после MVP.
2. **Показывать ли «надлом» пользователю?** Нет, пока нет валидации (M4) — только в отладочном виде.
